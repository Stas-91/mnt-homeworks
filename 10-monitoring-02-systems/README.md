- HTTP-запросы (латентность, пропускная способность, ошибки) - Поскольку взаимодействие с платформой идет через HTTP, эти метрики покажут, насколько быстро и надежно система отвечает пользователям. 2. Менеджер продукта посмотрев на ваши метрики сказал, что ему непонятно что такое RAM/inodes/CPUla. Также он сказал, 
что хочет понимать, насколько мы выполняем свои обязанности перед клиентами и какое качество обслуживания. Что вы 
можете ему предложить?
### Решение 2  
- RAM (оперативная память): Это объем памяти, который сервер использует для обработки запросов. Если RAM заканчивается, сайт или приложение клиента может замедляться или "зависать". Например, высокий уровень использования RAM может указывать на перегрузку сервера, что ухудшает пользовательский опыт.
- Inodes: Это количество файлов или объектов на сервере. Каждый файл, папка или даже email занимает один inode. Если лимит inodes исчерпан, клиент не сможет создавать новые файлы, что может нарушить работу сайта или сервиса.
- CPUla (CPU Load Average): Это показатель загрузки процессора сервера за определенное время. Высокая нагрузка (например, значения выше количества ядер процессора) означает, что сервер перегружен, что может привести к задержкам в обработке запросов клиентов.
- SLA (Service Level Agreement) Compliance: Проверить, выполняются ли договорные обязательства по доступности сервиса
- Время ответа сервера (Response Time): Показывает, как быстро сервер обрабатывает запросы клиентов
- Количество инцидентов и время их устранения (MTTR): Сколько раз возникали сбои и как быстро они решались
    
  Что предложить: Создать ежемесячный отчет с ключевыми метриками SLA, времени ответа и MTTR, чтобы менеджер видел, как выполняются обязательства

5. Опишите основные плюсы и минусы pull и push систем мониторинга.
### Решение 5
### Pull-системы мониторинга 

**Плюсы**:
- Централизованный сбор данных, упрощает управление.
- Гибкость в настройке интервалов опроса.
- Хорошо масштабируется для большого числа целей.

**Минусы**:
- Задержка в получении данных из-за периодического опроса.
- Нагрузка на сеть при частом опросе.
- Сложность мониторинга краткосрочных событий.

### Push-системы мониторинга 

**Плюсы**:
- Мгновенная отправка данных, подходит для реального времени.
- Меньшая задержка при обнаружении событий.
- Простота интеграции с системами, отправляющими метрики.

**Минусы**:
- Высокая нагрузка на сервер при большом числе источников.
- Сложность управления потоком данных.
- Риск потери данных при сбоях сети.

6. Какие из ниже перечисленных систем относятся к push модели, а какие к pull? А может есть гибридные?

    - Prometheus 
    - TICK
    - Zabbix
    - VictoriaMetrics
    - Nagios
### Решение 6
### Классификация систем мониторинга по моделям push и pull с учетом Pushgateway для Prometheus

- **Prometheus**: Основана на pull-модели, периодически опрашивая (scraping) метрики с конечных точек HTTP. Однако **Pushgateway** позволяет временно принимать push-метрики от краткосрочных задач (например, batch jobs), которые затем Prometheus опрашивает по pull. Это делает Prometheus гибридной системой, но Pushgateway используется только для специфических случаев, а основа остается pull.
- **TICK**: Основана на push-модели, где агенты (например, Telegraf) отправляют метрики в InfluxDB. Kapacitor с версии 1.3 поддерживает pull для Prometheus-совместимых целей, что делает систему гибридной.
- **Zabbix**: По умолчанию использует pull-модель, где сервер запрашивает данные у агентов, но поддерживает "активные проверки" (active checks), при которых агенты отправляют данные, что делает систему гибридной.
- **VictoriaMetrics**: Основана на pull-модели, аналогично Prometheus, но может принимать push-метрики через remote write или push-протоколы, что делает её гибридной.
- **Nagios**: Традиционно использует push-модель, где агенты отправляют данные на сервер, но может работать в pull-режиме через протоколы вроде SNMP или NRPE, что делает систему гибридной.

9. Изучите список [telegraf inputs](https://github.com/influxdata/telegraf/tree/master/plugins/inputs). 
Добавьте в конфигурацию telegraf следующий плагин - [docker](https://github.com/influxdata/telegraf/tree/master/plugins/inputs/docker):
```
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
```

Дополнительно вам может потребоваться донастройка контейнера telegraf в `docker-compose.yml` дополнительного volume и 
режима privileged:
```
  telegraf:
    image: telegraf:1.4.0
    privileged: true
    volumes:
      - ./etc/telegraf.conf:/etc/telegraf/telegraf.conf:Z
      - /var/run/docker.sock:/var/run/docker.sock:Z
    links:
      - influxdb
    ports:
      - "8092:8092/udp"
      - "8094:8094"
      - "8125:8125/udp"
```

После настройке перезапустите telegraf, обновите веб интерфейс и приведите скриншотом список `measurments` в 
веб-интерфейсе базы telegraf.autogen . Там должны появиться метрики, связанные с docker.
